How to use this

This isn't a copy of our code. It's the order we built things in, the main ideas that hold the code together, and what surprised us. That works for any robot, whether it shoots, throws, lifts or stacks.

Each step has:

  • A goal: what should work when you're done.
  • Sub-steps: do them in order. Don't skip the testing ones.
  • "From our robot" (green boxes): real things that happened to us, as examples.
  • "On your robot" (dashed boxes): how the same idea might look on a different robot, like a catapult.
  • Watch outs (red boxes): mistakes that cost us time.

The rule for every step: build a little, test it on the robot, then move on. If you write five things before testing any of them and something breaks, you won't know which one did it.

How robot code is shaped

Robot code runs in a loop. Many times every second, the robot does the same four things:

  1. 1. Readthe gamepad and sensors
  2. 2. Decidewhat each part should do
  3. 3. Do itset motor and servo powers
  4. 4. Write it downone row in the log

The code is split into pieces, and each piece has one job. This shape works for any robot:

flowchart TD
  OP["OpMode (TeleOp or Auto)"] --> R["Robot (the boss)"]
  RC["RobotConstants"] -.-> R
  R --> D["Drivetrain"]
  R --> A["Mechanism A (e.g. intake)"]
  R --> B["Mechanism B (e.g. shooter)"]
  R --> C["Mechanism C (e.g. indexer)"]
  OP --> L["Logger"]
  • OpMode: the program you pick on the Driver Station, like "Match TeleOp" or an autonomous.
  • Robot: the boss. It owns every part and makes the decisions that involve more than one part. On our robot: "only feed a ball when the shooter wheel is up to speed."
  • Subsystems (one per mechanism): each controls only its own motors and sensors. They never talk to each other. Only the Robot tells them what to do.
  • RobotConstants: every gamepad button in one place, plus numbers that more than one part uses.

How the folders are laid out

Every file has one home. Here's our project (everything lives inside TeamCode/src/main/java/org/firstinspires/ftc/teamcode/):

Plan your robot first

Before writing any code, list every mechanism and answer four questions about each one. Give this list to Claude at the start: it turns into your subsystems, states and rules.

  1. What hardware does it have? Motors, servos, sensors, and the names you'll give them.
  2. What can it be doing? These become its states, like IDLE, INTAKING, FIRING.
  3. How does it know it's "ready" or "done"? A sensor? A speed? A time?
  4. What can't run at the same time? These become rules in the Robot class.

Markdown files for Claude

Markdown (.md) files are plain text with simple formatting: # for headings, - for bullet points, **bold** for bold. Claude reads them easily. Set these up before you write robot code. We used three kinds.

1. CLAUDE.md: the rule book

Put a file called CLAUDE.md in the top folder of your project. Claude Code reads it automatically at the start of every chat, so you don't have to repeat your rules. You don't have to write it yourself: tell Claude the rule and why, and ask it to add it. Good rules are about how the code is organized, not just how it looks.

Ask Claude: code style

"Add a Code style section to CLAUDE.md: use long, easy-to-read variable names (poseFactory, not p), give every function a Javadoc comment, and comment any line that's hard to understand."

Ask Claude: how subsystems and the Robot class work together

"Add an Architecture section to CLAUDE.md. Every subsystem is a state machine: a State enum plus a switch in update() that sets the power every loop. Each subsystem owns its own hardware and never talks to another subsystem. Robot.java owns every subsystem and is the only place that decides which states they're in, including the robot's overall states and which mechanisms can't run together. Subsystems never read the gamepad."

Ask Claude: when to use command-based code

"Add a Command-based section to CLAUDE.md. The default is always enum + switch. Only use Ivy commands for steps that run in order with different 'done' rules (like autonomous), for two things at once or whichever-finishes-first, or for pieces reused across several autos. TeleOp and the mechanisms stay enum + switch. 'For consistency' is not a reason to switch."

Ask Claude: where things go

"Add to CLAUDE.md: RobotConstants holds only the whole gamepad button map and numbers more than one class uses. A number only one class uses goes in a labeled CONSTANTS block at the top of that class. Test autos go in opmodes/autonomous/tests."
  • Be specific. "Write good code" doesn't help. "Subsystems never read the gamepad" does.
  • Say why. Claude follows a rule better when it knows the reason.
  • Add a rule as soon as you catch Claude doing something you don't want. "You put button logic in the Intake class. Move it to Robot, and add a rule to CLAUDE.md so it doesn't happen again."
  • Ask Claude to check its work against it: "Does this change follow every rule in CLAUDE.md?"

2. Plan files: before you build

For anything that takes more than one session, ask Claude to write a plan file first. A good plan has the steps in order, how you'll check each one, and a checklist of things you have to give Claude: measurements, names, files.

Ask Claude

"Before we write any code for the catapult, write CATAPULT_PLAN.md: the steps in order, how we'll test each one on the robot, and a checklist of measurements and hardware names you need from us."

3. Status files: after every test

Every chat with Claude starts fresh. A status file is how the next chat knows where you left off.

Ask Claude

"Update CATAPULT_STATUS.md with today's test: what we tested and the log file's name, what we found (with numbers), what we changed in the code because of it, and what to do on the next test."

Then a new chat can start with: "Read CATAPULT_STATUS.md and tell me where we're at."

Tip

Claude Code also has memory: you can ask it to remember a decision for future chats. We used it to save "build our own flywheel speed control, but later."

Part 1 · The steps, in order

STEP 0

Set up your tools and rules

Goal: an empty project that builds, is saved on GitHub, and has rules for Claude to follow.

  1. Start from the official Pedro Pathing docs (pedropathing.com). Their Quickstart project already has the FTC SDK and Pedro set up for you. Open it in Android Studio and make sure it builds before you change anything.

    Ask Claude

    "Create a new project in the 2026-2027 BIOBUZZ folder called [insert project name] and initialize the project using the Pedro Pathing GitHub here: https://github.com/Pedro-Pathing/Quickstart.git"
  2. Put it on GitHub and commit. From now on, commit every time something works. That's your save point if something breaks later. (New to GitHub? See GitHub basics below.)
  3. Write your CLAUDE.md file first, before any robot code. It tells Claude your rules (see Markdown files for Claude above for prompts to build it).

    Ask Claude

    "Create a CLAUDE.md for this project. Rules: use long, easy-to-read variable names, give every function a Javadoc comment, each subsystem owns its own hardware, and Robot.java ties the subsystems together."
  4. Add any other libraries you need (for us, Ivy for autonomous commands) by following their install guides. Build again after each one.

    Ask Claude

    "Add the Ivy library to this project using its install guide: [link]. Then build the project and tell me if anything broke."

GitHub basics

GitHub keeps a copy of your code online, so the whole team shares one version and you can always go back to one that worked. You only need four words:

WordWhat it meansAsk Claude
CommitSave a snapshot of your code on your laptop, with a short note about what changed."Commit these changes with a message saying the intake works."
PushSend your commits up to GitHub so everyone else can get them."Commit and push to the main branch."
PullDownload the newest code from GitHub onto your laptop. Do this before you start working, so you have your teammates' changes."Pull the latest code from this repo."
BranchA separate copy to try something risky without breaking main, the version the robot runs."Make a new branch called catapult-test."

A normal day: pull at the start, commit each time something works, push before you leave.

Watch out
  • Always build after a change. One evening our Java setup was broken, so nothing was being compiled, and we kept making changes that had never been checked. If Claude says it couldn't compile, fix that first.
  • If the robot shows as "offline" or won't connect over USB, the adb tool is often stuck. Ask Claude to restart it (adb kill-server, then adb start-server).
  • Updating the SDK can break old sample files. When we moved to SDK 12, 37 errors came from old samples. Paste the errors into Claude: they usually point at the exact file.
STEP 1

Get the drivetrain going

Goal: the robot drives with the gamepad, knows where it is on the field, and can drive a path by itself.

The drivetrain comes first on every robot, because everything else depends on it. Aiming and autonomous both need the robot to know where it is, which is called localization. Our robot uses a goBILDA Pinpoint with two odometry pods (little wheels that roll on the floor and measure how far the robot moved).

  1. Set up the hardware configuration on the Driver Station: name every motor and sensor. The names in the code must match exactly.
  2. Go through the Pedro Pathing tuning guide in order. In Pedro 3 the tuners run from a web page on the robot (http://192.168.43.1:10158 when you're on the robot's Wi-Fi):
    1. Mecanum tuner: spins one wheel at a time to check each motor's direction, and measures how fast the robot drives.
    2. Pinpoint tuner: sets up the odometry pods.
    3. Foresight tuner: tunes how the robot follows a path (how hard it pushes, brakes and turns).
  3. Measure the pod offsets yourself: how far each pod is from the center of the robot. Measure with a ruler, or get the numbers from the robot's CAD. Don't trust the tuner's guess.

    Ask Claude

    "Our Pinpoint pod offsets are: x pod 6.5 in, y pod −2.5 in from the center of the robot (measured with a ruler). Put them in Pedro's Constants.java and tell me which direction is positive for each one."
  4. Run a localization test. Push the robot by hand and watch x, y and heading on telemetry. Forward should make x go up, left should make y go up, and turning left should make heading go up. If one goes the wrong way, flip that direction.
  5. Drive it with a simple TeleOp. We use field-centric driving: pushing the stick forward always moves the robot away from you, no matter which way it faces.

    Ask Claude

    "Create a TeleOp routine called [TeleOp name] that uses field-centric driving. The routine should just let the robot drive around using the driver controls. The robot's pose should display on telemetry, and the back button on the controller should reset the robot's pose to (0, 0, 0)."
  6. Test with tiny autos that each do one thing. We recommend making these two:
    • OutNBack5ft: drives 5 ft straight out, turns 180°, then drives back to where it started. This checks that the robot drives the right distance, turns accurately, and follows a path well.
    • Turn360: turns in place a full circle, pausing every 90°. This checks the pod offsets. If they're wrong, x and y drift while the robot turns, even though it never moved.

    Put them in their own folder, opmodes/autonomous/tests/, so test autos never get mixed up with match autos.

    Mark the start spot with tape. If the robot ends on the tape and telemetry still reads close to (0, 0, 0), your tuning and offsets are good, and you can trust autonomous later. If not, these tests tell you which part to fix.

    Ask Claude

    "Create a test autonomous called OutNBack5ft in a folder called tests inside the autonomous folder. The robot starts at (0, 0, 0), drives forward 5 ft, pauses for 1 second, turns 180°, pauses again, then drives back to the start. Show the target pose and the actual pose on telemetry the whole time."

    Ask Claude

    "Create a test autonomous called Turn360 in the autonomous/tests folder. The robot starts at (0, 0, 0) and turns in place a full 360° in 90° steps, pausing 1 second at each step. Show x, y and heading on telemetry so I can see if x and y drift while it turns."
From our robot
  • Measure the pod offsets by hand. The tuner gave x = −4.83 in, y = −8.95 in. Measured with a ruler they were x = 6.5 in, y = −2.5 in. Wrong offsets make the position drift every time the robot turns.
  • Check every direction. Our localization test showed the x pod was reversed.
  • Pedro 3 has no "turn" command, and a path can't have zero length. To turn in place, hold the same spot with a new heading, in 90° steps.
  • Odometry can be fooled. When our robot slammed into a wall, the pods skidded and added 33 inches of fake travel. Normal drift was about 5 inches over 3–4 minutes. Later steps deal with this.
STEP 2

Add your first mechanism

Goal: one simple mechanism works from the gamepad, and you've learned the pattern every other mechanism will copy.

Start with the simplest mechanism, usually the intake. You don't write it line by line. Your job is to describe the mechanism clearly, and Claude writes the code. Before you prompt, write down:

  1. What it does, in one or two plain sentences. "The intake spins rollers that pull balls into the robot."
  2. What hardware it uses: how many motors, servos and sensors, and what kind (a goBILDA motor? a continuous servo?).
  3. The exact names from the hardware configuration on the Driver Station. These must match the code.
  4. What it can be doing (its states) and which button does each one.
  5. Ask Claude to build it, then test it. If something spins the wrong way, tell Claude which part and which way.

Ask Claude

"Create an Intake subsystem. It spins two rollers that pull balls into the robot. Hardware: two goBILDA motors named 'intakeLeft' and 'intakeRight' in the hardware config. It should be able to stop, pull balls in, and push them out. Holding right bumper pulls in, holding left bumper pushes out, and letting go stops it. Add it to our TeleOp so I can test it. Build it and tell me how to test it."

Ask Claude

"The intake's left roller spins backwards when I press right bumper. Fix the direction."

Here's the kind of code you should get back. It's short because CLAUDE.md tells Claude to use our pattern:

public enum State { IDLE, INTAKING, OUTTAKING }

public void update() {            // runs every loop
    switch (state) {
        case IDLE:      setPowers(0.0);  break;
        case INTAKING:  setPowers(1.0);  break;
        case OUTTAKING: setPowers(-1.0); break;
    }
}

Our intake (Intake.java). This "enum + switch" shape is called a state machine. It's our default for every mechanism.

From our robot
  • Set the power every loop, even if the state didn't change. An early version skipped the update when the state was "the same," and the intake got stuck on.
  • When a part won't move, test the wiring first. We made a test OpMode where button A drove the motor directly and button B drove it through our code. If A works and B doesn't, the bug is in the code.
STEP 3

Add logs (the step that helped most)

Goal: every test run saves a file Claude can read to tell you what happened.

Telemetry is gone the moment it scrolls past. A log saves everything to a file on the robot: one row for every loop, one column for every value. We almost never read the logs ourselves. We tell Claude what we did during the test, Claude pulls the file off the robot and reads it, and we ask it questions. Almost every hard bug this season was found that way.

Do this right after your first mechanism works, before you build anything harder. We added ours later than we should have.

Ask Claude to set up logging

Ask Claude

"Add a CSV logger that writes one row every loop to a file on the robot, with the OpMode name and time in the file name. It should never crash the OpMode if the file can't be written. Log the time, the robot's pose, the buttons pressed, and the intake's state and power."

You don't need to know how to get the files off the robot. Claude does that. Your job is to tell it what happened and ask it to investigate:

Ask Claude

"Our robot overshot our first shot and then undershot our second shot. Look into the logs and investigate what happened to the shooter."

Our version is logging/CsvLog.java. It saves files in /sdcard/logs/ with names like MatchAuto2Red_2026-10-14_11-52-23.csv.

What to log

You don't design the columns; Claude does. For every new mechanism, ask it to log what the part was told to do, what it actually did, its state, and why it made each decision. Also log the battery voltage, which helps spot hardware problems. When a test leaves you confused, ask: "What would you add to the log to figure this out next time?"

How to test with logs

  1. Ask Claude for a test procedure before you go to the field: what to do, in what order, and what should happen.
  2. Take notes while you test. "Started in the corner. At about 1:20, flipped the cells. Parked at the Red_Flower spot." Times and places help Claude find the right part of the log.
  3. Ask Claude to read the log, give it your notes, and ask specific questions.
  4. Before changing code, ask Claude to try the fix on the old log. If the new rule would have worked last time, it'll probably work next time.

Ask Claude

"I just ran a test. Here's what I did: [your notes, with times]. Pull the newest log off the robot and tell me: did the robot do what it should? Was anything way off? What happened at 1:20?"

STEP 4

Add the scoring mechanism

Goal: the part that scores does the same thing every time.

This is the hardest mechanism, because scoring needs to be repeatable. A shot or a throw only lands in the same place if the mechanism is in the same condition every time: the same speed, the same angle, the same pull-back.

  1. Control the thing that matters, not just the power. For a flywheel that's speed: we use the motor's velocity control, so the speed holds even as the battery drains. For an arm, it's usually position.
  2. Show the target and the actual value on telemetry, side by side. You can't tune what you can't see.
  3. Find good settings on the field. We added buttons that bump the target speed up or down 50 RPM while driving, then saved the best value in the code.

    Ask Claude

    "In the TeleOp, make the right bumper raise the shooter's target speed by 50 RPM and the left bumper lower it by 50 RPM, once per press. Show the target and actual RPM on telemetry, and add both buttons to the button map in RobotConstants."
  4. Decide exactly what "ready" means. Ours: start feeding once the wheel is within 45 RPM of the target, and stop if it drifts more than 90 RPM away. Two different limits stop it flickering on and off.
  5. Tune the controller (PID) by asking Claude to compare target and actual in the log.

    Ask Claude

    "I shot 4 balls from the start spot. Pull the newest log and compare the target and actual wheel speed. Is it overshooting or slow to recover? Suggest new PID values and explain why."
From our robot
  • Know how precise your sensor is. The hub reads our wheel speed in jumps of about 43 RPM. Limits smaller than one jump just cause flicker.
  • Hardware problems can look like code problems. When our flywheel started overshooting, the first guess was a weak battery. The logs showed an Expansion Hub was losing power, which made it forget our controller settings. The fix was a new power cable, and sending the settings again at the start of every shot.
  • Scoring changes the mechanism. Each ball slowed the wheel by 100–190 RPM. Plan for it.
On your robot

A catapult might be a motor pulling an arm back, held by a latch, and released by a servo. The same ideas apply:

  • Control how far it pulls back (with an encoder or a limit switch), so every throw starts the same.
  • Define "armed" exactly, and only allow firing once it's armed.
  • Show the target and actual pull-back on telemetry.
  • Ask what changes from throw to throw: a stretching band, a warming motor, a low battery?
STEP 5

Connect the mechanisms (hand-offs)

Goal: game pieces move from one mechanism to the next only when the next one is ready.

Most robots pass game pieces along: intake → something in the middle → scorer. Here's how it worked on ours.

Our indexer

Our first problem was the intake pushing balls into the shooter before the wheel was up to speed, so shots came out weak. The fix was an indexer: an Axon servo that sits between the intake and the shooter wheel and feeds balls in only when the shooter is ready.

  • It has three states. HOLDING (no power, the normal state), FEEDING (spins to push balls into the wheel), and CORRECTING (turns back to a rest position).
  • A PID control holds it at a rest position. The servo has a feedback wire that reports its angle. There's a rest angle every 90°. When it's off rest, the PID turns it to the nearest one: harder when it's far away, gentler as it gets close, so it stops on the spot instead of overshooting.
  • It corrects twice per shot: once while the shooter spins up (it gets knocked off rest while it has no power), and once after feeding stops.
  • The Robot class decides when it feeds. The indexer doesn't know the shooter exists. Robot checks "is the wheel at speed?" and only then tells the indexer to feed.
  • The PID math is in its own class (IndexerMath), so Claude wrote unit tests for it that run on the laptop, with no robot.

Ask Claude

"Create an Indexer subsystem for an Axon servo named 'indexer', with its angle feedback on an analog input named 'indexer_encoder'. States: HOLDING, FEEDING, CORRECTING. In CORRECTING, use a PID to turn it to the nearest rest angle (every 90°). Put the PID math in IndexerMath and write unit tests for it. Robot should only let it feed when the shooter is at speed."
From our robot
  • A wrong direction sign makes a PID fight itself. With the sign backwards, our indexer pushed away from rest and swung back and forth by up to 45°. The log showed which way the angle really moved.
  • Save the rest position once and reuse it. Our auto once ended with the indexer 8° off, and the next OpMode saved that as its new zero. Now zero is saved at the first start-up and kept across OpModes.
On your robot

The catapult robot has an indexer too, plus a flower ramp that helps it. The same rule applies: the indexer only lets a piece through when the catapult is armed and ready to hold it. The flower ramp makes this trickier because it has more than one job, and that's exactly what the Robot class is for (see Step 6).

STEP 6

Organize: one Robot class in charge

Goal: the code is easy to find your way around, and only one place decides how the parts work together.

Once you have more than two mechanisms, rules like "don't intake while scoring" start showing up everywhere. Put all of them in one place: the Robot class. We did this early on, then cleaned it up as the robot grew.

  1. Make Robot.java. It creates every subsystem, and it's the only place the hardware gets set up.
  2. Move the decision rules into it: reading the gamepad, what can't run together, and when hand-offs happen.
  3. Give the robot overall states (ours: IDLE, INTAKING, OUTTAKING, SHOOTING). Each one says what every subsystem must be doing.
  4. Make RobotConstants.java with the whole gamepad button map, so any control can be changed on one line.

    Ask Claude

    "Create a Robot class that owns the intake and shooter, and move the rule 'don't intake while shooting' into it. Put every gamepad button in RobotConstants. Don't change how the robot behaves."
  5. Write these rules into CLAUDE.md so Claude follows them every time.
Our architecture rules (from CLAUDE.md)
  • Each subsystem owns its own hardware. Nothing else touches it.
  • Robot owns all subsystems and holds the logic that ties them together.
  • RobotConstants is only for things more than one class uses. A number only one class uses goes at the top of that class, in a labeled CONSTANTS block.
From our robot

Clean up once things work, not before. Our RobotConstants grew to 278 lines; moving one-class numbers into their own classes brought it down to 89. Each cleanup came after a test showed the code worked.

On your robot: the flower ramp

The catapult robot has three mechanisms that have to work together: an indexer, the catapult (the shooting system), and a flower ramp. The flower ramp has several jobs, and they depend on what the rest of the robot is doing:

  • Near a flower, it moves so the indexer can pick up pieces more easily.
  • While holding pieces, it blocks them from flying out of the hopper.
  • While driving, it has to sit in a set position.
  • While shooting, it has to move out of the catapult's way.

The flower ramp can't decide any of this by itself, because it doesn't know what the catapult or the drivetrain is doing. So the Robot class picks one robot state, and that state sets every subsystem's state at once:

Robot stateFlower rampIndexerCatapult
DRIVINGDriving position (keeps pieces in the hopper)HoldingArmed or resetting
INDEXING (at a flower)Indexing positionIndexingArmed, waiting
SHOOTINGOut of the way firstFeeds once the ramp is clearFires once the ramp is clear

"Don't fire until the ramp has moved" is a rule between two subsystems, so it lives in Robot, not in either subsystem.

Ask Claude

"In Robot.java, add robot states DRIVING, INDEXING and SHOOTING. In each one, set the flower ramp, indexer and catapult states from this table: [paste the table]. In SHOOTING, move the flower ramp out of the way first, and only let the catapult fire once the ramp says it's clear. Log the robot state and why it's waiting."
STEP 7

Automate scoring

Goal: one button lines the robot up, picks the right setting for where it is, and only scores when everything is ready.

On our robot, holding the trigger turns the robot to face the target, picks the shooter speed for that distance, and only feeds when it's lined up. The steps work for any scorer:

  1. Measure real scoring. From several spots, find the settings that work. Write down every measurement, and ask Claude to keep them in a comment in the code.
  2. Build a table: distance → setting. For a distance between two rows, the code blends the two (that's called interpolation). Ours is distance → RPM in ShotTable.java.
  3. Measure against one hive cell, then use symmetry for the rest. Every shot measurement and the whole shot table were taken against one cell: the blue hive's lower cell, which is in the lower-right quadrant of the field in the Pedro Pathing visualizer. The code stores only that cell's position, and works out the other three from it:
    • Blue upper: flip the measured cell over the field's horizontal center line.
    • Red upper: turn the measured cell 180° around the center of the field.
    • Red lower: flip red upper over the horizontal center line.

    The distances are the same by symmetry, so one shot table works for all four cells.

    Watch out

    Write down exactly which cell and which quadrant you measured in, in the code and in your prompt. "The hive" isn't enough. If Claude guesses the wrong one, the flip puts every other target in the wrong place, and aiming is off on the whole field.

    Ask Claude

    "All our shot measurements were taken against the blue hive's lower cell, in the lower-right quadrant of the Pedro Pathing visualizer, at (81.45, 56.06). Store only that cell. Work out blue upper by flipping it over the field's horizontal center line, red upper by turning it 180° around the field center, and red lower by flipping red upper. Write unit tests that check all four positions."
  4. Unit test the math on your laptop. Ask Claude to write the tests.
  5. Wire it to one button, and only allow scoring when every condition is met. Ours: facing within 3°, in range, wheel at speed.

    Ask Claude

    "Here are my shot measurements: [distance → RPM list]. Build a ShotTable that blends between rows, write unit tests for it, and keep my measurements in a comment."
From our robot
  • Trust your measurements over a neat line. Our speed table dips in the middle: up close, the ball needs extra speed to clear the edge of the target. The code says "Don't smooth it into a line."
  • Tune in small steps, and write down why. We lowered every row by 25 RPM when shots went high, then raised them by 20 when they came up short. Each change is noted next to the numbers.
  • Always keep a manual backup. One button scores at a fixed setting with no aiming, for when the position is wrong.
On your robot

For a catapult, the table might be distance → pull-back amount (or launch angle). The rest is the same: measure, build a table, test the math, keep a manual backup.

STEP 8

Autonomous with Ivy commands

Goal: an autonomous that runs a list of steps in order, where each step waits until it's really done.

First: how the auto files are organized

Before writing any routine, set up three layers. This way you never write the same code twice, and you never write a separate red and blue version of a routine.

flowchart TD
  BASE["MatchAutoBase (one main auto class)"] --> R1["MatchAuto1 (routine: wait for partner)"]
  BASE --> R2["MatchAuto2 (routine: shoot right away)"]
  R1 --> RED1["RedMatchAuto1"]
  R1 --> BLUE1["BlueMatchAuto1"]
  R2 --> RED2["RedMatchAuto2"]
  R2 --> BLUE2["BlueMatchAuto2"]
  1. One main auto class (ours is MatchAutoBase). Everything every auto needs goes here, once: creating the robot, start-up checks, logging, the scoring command, and the forAlliance() helper.
  2. Routines built on top of it (MatchAuto1, MatchAuto2). Each one only lists its own steps and poses. Every pose is written for the red side.
  3. An alliance wrapper for each routine (RedMatchAuto1, BlueMatchAuto1, …). Each one is a few lines: an alliance() function that returns RED or BLUE. These are the only ones that show up on the Driver Station.

How the alliance works: the field is symmetric, so blue's spots are red's spots turned 180° around the center of the field. Every pose in a routine goes through forAlliance(), which leaves it alone on red and turns it on blue. The auto also saves the alliance, so the TeleOp after it knows which side it's on without the driver choosing.

Ask Claude

"Create a main autonomous class called MatchAutoBase that every match auto extends. It sets up the robot, logging and start-up checks, and has an alliance() function that each auto fills in with RED or BLUE. Add a forAlliance() helper that takes a red-side pose and turns it 180° around the field center for blue. Then make a routine called MatchAuto1 with red-side poses, and RedMatchAuto1 and BlueMatchAuto1 wrappers that only pick the alliance."

Ask Claude

"Add a new routine MatchAuto3, built on MatchAutoBase, that drives from the start to [pose], shoots, then parks at [pose]. Add red and blue wrappers named Red_Auto3 and Blue_Auto3."

Why Ivy

A state machine is great for one mechanism. An autonomous is different: it's a list of steps, and each step has its own "done" rule (arrived at a spot, finished scoring, a timer ran out). For that we use Ivy, a command library made for Pedro Pathing.

The Ivy building blocks we use

BlockWhat it does
sequential(a, b, c)Do a, then b, then c.
race(a, b)Run both at once and stop when either one finishes, for example "aim until ready, or give up after 3 seconds."
waitUntil(...)Wait until something is true.
waitMs(...)Wait a set time.
instant(...)Do one thing right away, like stopping the drivetrain.
 
return sequential(
    markStep("nudgeOffWall", shootPose),
    robot.drivetrain.followPathCommand(straightPath(startPose, shootPose)),
    markStep("aimAndShoot", null),
    aimAndShootCommand(),
    markStep("park", parkingPose),
    robot.drivetrain.followPathCommand(straightPath(shootPose, parkingPose))
);

A shortened version of one of our autos. markStep() writes the step's name into the log.

  1. Hook Ivy into the OpMode: call Scheduler.reset() in init() and Scheduler.execute() in loop().
  2. Make "done" mean really done. Our drive commands finish only when the robot is actually at the target, not when the path is finished on paper.
  3. Test on red first, then blue. If red works and blue doesn't, the problem is in a pose that skipped forAlliance().
  4. Test every leg, and ask Claude to use the log's step names to find where time went.

    Ask Claude

    "I ran Red_NoPause and it took 4 seconds too long. Pull the newest log and tell me which step took the most time and why."
From our robot
  • Ivy's built-in drive commands finish too early. Ours wait until the robot has settled at the target.
  • Always call Scheduler.reset() in init(). Otherwise leftover commands from the last OpMode would keep running.
  • Use Ivy only where it earns its place: steps in order, two things at once, or "whichever finishes first." Mechanisms and TeleOp stay plain state machines.
  • Plan around your alliance partner. We have one auto that waits 15 seconds so the partner can score first, and one that scores right away.
STEP 9

Match OpModes and safety checks

Goal: the auto hands off smoothly to TeleOp, and drivers hear about problems before they cost points.

  1. Carry the position from auto into TeleOp, plus which alliance you're on, so the driver doesn't have to set anything.
  2. Fix the controls for each side. Our blue driver stands across the field, so their stick directions are turned 180°.
  3. Check things at INIT. Our robot checks that the start position stuck (the Pinpoint can lose one set too early) and says "Odometry OK" or "ODOMETRY ERROR."

    Ask Claude

    "At INIT, check that the start pose actually stuck, and show 'Odometry OK' or 'ODOMETRY ERROR' as the top line of telemetry."
  4. Warn when something is impossible. If the position says the robot is inside a wall for 5 loops in a row, telemetry shows "ODOMETRY OFF – USE MANUAL SHOOTING." Waiting for 5 loops means one bad reading won't set it off.
  5. Keep telemetry short, with the most important line on top. Drivers only glance at it.
  6. Name OpModes so drivers can't pick the wrong one, for example Red_Flower_Pause and Red_NoPause.
STEP 10

Limelight

Goal: the Limelight camera fixes odometry drift, but only when its reading can be trusted.

Our robot always has a Limelight camera. It reads the AprilTags on the field and works out where the robot is, which fixes the drift the odometry builds up over a match (and the big jumps after a crash). Do this after everything else works.

  1. Ask Claude for a plan file first. Ours is LIMELIGHT_VISION_PLAN.md: the steps in order, and a checklist of measurements the team has to provide.

    Ask Claude

    "We want to use our Limelight 3A to correct odometry using the AprilTags on the hive. Write a plan file, LIMELIGHT_VISION_PLAN.md, with the steps in order, how we'll test each one, and a checklist of everything you need from us."
  2. Make a field map (.fmap) file. It lists every AprilTag's ID and exactly where it sits on the field. Make it from the field's CAD. Ours is BIOBUZZ HIVE.fmap.
  3. Upload the .fmap to the Limelight from its web page. With the laptop plugged into the Limelight, that's usually http://limelight.local:5801. With the Limelight on the robot and your laptop on the robot's Wi-Fi, try http://172.29.0.1:5801. If neither loads, check the Limelight docs for your model.
  4. Set it up on the web page:
    • Where the camera is on the robot: forward/back, left/right and height from the robot's center, plus how far it tilts up. Get these from CAD.
    • Cropping: crop the image to where tags can actually show up, so the camera doesn't waste time on the floor or on parts of the robot.
    • The AprilTag pipeline: the game's tag family and tag size (from the CAD), with full 3D turned on.
    • Name it limelight in the Control Hub's hardware configuration.
  5. Start with a test OpMode that only watches. It shows and logs the Limelight's position next to the odometry's, without changing anything. Drive around, stop in front of tags, and let Claude compare the two in the log.

    Ask Claude

    "Make a test TeleOp called LimelightCoordinateTest. It drives like our normal TeleOp, but also shows and logs the Limelight's robot position next to the odometry's position, plus every tag it sees. Don't let the Limelight change the odometry yet."

    Ask Claude

    "I drove around and stopped in front of the hive 6 times. Read the newest LimelightCoordinateTest log and compare the Limelight's position to odometry at each stop. When were they close, when were they far apart, and why?"
  6. Decide exactly when the Limelight is allowed to update the odometry. Ours: only x and y (never heading), at most once per stop, only when the robot is still, the tags are still in the image, and all the good tags agree within 3 in.

    Ask Claude

    "Using the last two logs, suggest rules for when the Limelight should correct the odometry. Replay the rules on the logs and tell me how many updates each would have made and how far off they were. Don't change the robot code until I agree."
  7. Turn it on and test in a match-style run, then ask Claude to check every correction in the log: when it happened, and how far it moved the odometry.
Limelight tips from our robot
  • Check the web page settings against the logs. CAD said the camera was tilted 45°. The logs fit 42° best, so we use 42° in the code.
  • Our camera faces backward. Leaving yaw at 0 on the web page worked for position, but made the Limelight's heading read 180° off. We fixed that in code and left the web page alone. Write down choices like this so nobody "fixes" them later.
  • MegaTag2 didn't work for us. It was 22 in off. Turning it off also made each loop faster (22 ms down to 16 ms).
  • Pieces in front of the camera block it. About half the loops while shooting had no reading. The rules skip those loops instead of starting over.
  • Facing a tag straight on can flip its angle, which made the position jump 9–23 in. We now work out position from where the tag is in the image, not which way it's turned.
  • Tags on a tipped-down cell look upside down to the camera. We ignore those tags.
  • Limits from a calm test can fail in a real match. Our "robot is still" limits came from a robot sitting completely still. While aiming and shooting it wobbles, so nothing updated until we loosened them using the match log.
  • Check it's plugged in. Our first camera test recorded nothing at all. Now telemetry shows LIMELIGHT NOT CONNECTED at INIT.

The full story is in LIMELIGHT_STATUS.md: a good example of a status file kept up to date after every test.

Part 2 · Working with AI

Writing good prompts

A prompt is what you type to Claude. Good prompts get working code the first time. Before you hit Enter, answer these questions:

The prompt checklist

AWhat inputs will Claude need?
Which files or mechanisms? The exact hardware names? Measurements, with units? The whole error message, pasted in? Your notes from the test (what you did, and when)?
BHow will you check that it worked?
Does it build? Is there a unit test? What will telemetry or the log show? What exactly will you do on the robot to test it?
CWhat does "done" look like?
Describe what the robot should do, not just "fix it." "When I press A, the catapult pulls back, waits until it's armed, and only then lets me fire."
DWhat should Claude not change?
"Don't touch the drivetrain." "Just explain it, don't change any code yet."

Before and after

Vague

"The shooter is broken, fix it."

Clear

"In TeleOp the first shot goes long, and the rest are fine. Pull the newest log off the robot and compare the target and actual wheel speed around each shot. Tell me what you find before changing any code. To test the fix, I'll shoot 4 balls from the start spot."

Vague

"Explain this error."

Clear

"I get this error when I press INIT on DriveTest: [paste the whole error]. I just renamed the intake motor in the hardware config to 'intake'. What's wrong?"

Prompts that worked well for us

  • "Before we do anything, let's figure out the steps we should take, in order." Get a plan before code.
  • "What do you need from me to do this?" Let Claude tell you what's missing.
  • "Push back on anything that doesn't make sense." Claude did, and it was right.
  • "Explain how this works. Don't change any code." Great for learning.
  • "Here's what I did in the test: [notes with times]. Look at the logs and tell me what happened."
  • "What would you add to the log to figure this out next time?"
  • "Write a test procedure for the next run, and add it to the status file."

Habits that saved us

  1. Build a little, test a little. One change, one test, then commit.
  2. Make sure it compiles. Code that was never built is not done.
  3. Log it. If you ever wonder "what was it doing?", the log needed one more thing.
  4. A first theory is a guess, not a fact. "It's the battery" turned out to be a hub losing power. Ask Claude: "What would prove or disprove that?"
  5. Try new rules on old logs before trying them on the robot.
  6. Measure it yourself when it matters: offsets, distances, angles.
  7. Write down why a number is what it is, right next to it in the code.
  8. Make silent failures loud. A missing sensor or a bad position should show up on telemetry.
  9. Test the way you'll play. Settings tuned on a robot sitting still can fail during a real match.
  10. Read what Claude changed. You're the engineer. Ask it to explain anything you don't understand.

Word list

OpMode
A program you choose on the Driver Station (a TeleOp or an Autonomous).
Loop
The part of an OpMode that runs over and over, many times a second.
Subsystem
One mechanism and its code, like the intake or the catapult.
State machine
A list of states (an enum) plus a switch that does the right thing for each one.
Telemetry
Text the robot shows on the Driver Station while it runs.
Pose
Where the robot is and which way it faces: x and y (inches) and heading (degrees).
Odometry
Working out the pose by measuring how far the wheels or pods have rolled.
Pedro Pathing
The library that drives the robot along paths and tracks its pose.
Ivy
A library for running commands in order, at the same time, or as a race.
Encoder
A sensor that measures how far a motor or arm has turned.
RPM
Revolutions per minute: how fast a wheel spins.
PID
A controller that keeps adjusting power to reach a target, like a speed or an angle.
Hysteresis
Using two limits (one to turn on, a bigger one to turn off) so something doesn't flicker.
Log (CSV)
A file with one row per loop and one column per value. Claude reads it for you.
adb
The tool that talks to the robot over USB, for example to pull logs off it.
Unit test
A small program that checks your math on the laptop, with no robot.
Markdown
Plain text with simple formatting. Files end in .md.
